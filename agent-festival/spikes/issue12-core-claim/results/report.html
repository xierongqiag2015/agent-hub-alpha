结论
  1. 方案在真实 Core 0.1.17 上可行。业务节点用 WorkflowComponent 包装后，先向 Go 认领 o，再提交唯一正式结果。12 个场景（含子工作流、3 轮循环、中断等待）全部满足“每个 o 至多一条正式结果、业务效果 1 次”。
  2. 对照组复现了缺口。在同一个崩溃点不经控制面时，Core 没有留下检查点，整张图从头重跑：S1 模型调用 2 次，同一笔授信放了 2 次。
  3. 源码阅读的结论得到实测确认：
    • 循环 3 轮的 executableId 都是 loop.supplement，o 必须由外部按轮次分配；
    • kill -9 不留检查点，要靠同一个 T 整图重跑，再由包装组件复用已提交的结果；
    • 中断恢复时，被中断的节点从开头重跑；
    • 子工作流内部拿到的是同一个 T。
  4. 新发现的设计约束（见局限与下一步）：
    • 租约必须续约，否则两个活着的进程会轮流接管；
    • 派发隔离目前只做到签发许可这一步，要在出口实时拦住旧代次需要出口代理（P04）；
    • 提交时要先判重复、再判代次。

控制面Go 1.24.9 + modernc SQLite（WAL，单连接串行事务）。不变量写成唯一约束和条件更新，在同一个事务里完成：results(o) PK、owner 代次比较、K 有效性复查、B 状态机
崩溃Runtime.getRuntime().halt(137)，不执行 finally 和关闭钩子，等价于 kill -9
替身S1/S2 为确定性替身（计数）；银行 API 按键幂等、可查询，可注入延迟和受理中状态

事实实测场景对方案的影响
循环每轮的 executableId 相同（loop.supplement），子工作流节点为 kyc.kyc_checkE1o 必须由 Go 按 (T,node,iter) 分配；轮次靠 ${loop.index} 输入映射
进程被杀时不留检查点，重跑从图的开头执行C0、E2a–E2c恢复 = 同一 T 整图重跑 + 包装组件复用；检查点不能作为业务进度
中断等待会写持久检查点，恢复时只跑被中断的节点，且从节点开头重跑E2d被中断节点必须先读 Go 记录；恢复输入只是提示，不是事实
子工作流内部的 sessionId 与父图相同E1子工作流节点可以直接参与同一个 T 的 o 分配
默认工作流 ID 是随机 UUID探针跨进程恢复必须固定工作流 ID，否则找不到检查点

局限与下一步

本次未覆盖 / 已知约束

  • 模型与业务 API 都是替身；没有经过 Runtime 的 HTTP/A2A 路径，没有接 WorkSwarm。
  • 控制面单实例；租约固定不续约。节点执行时间超过租约时，两个活着的进程会轮流接管，生产环境需要心跳续约。
  • 派发隔离做在签发许可这一步。旧进程如果已经拿到许可、又延迟发送，只能靠提供方幂等键兜底；要在出口实时校验代次，需要出口代理（P04）。
  • 提交要先判重复、再判代次（E3b2）：旧进程在新 owner 提交之后复活，会被识别为重复并采用已有结果，不报“代次过期”。
  • Windows 单机实测，未做性能测试。E1 中 8 个业务节点（含控制面调用和 1 次 API）首次执行约 140 ms，全部复用的重跑约 60 ms（不含约 0.4 s 的 JVM 与 Core 初始化）。

  2. 出口代理与派发令牌（P04），在出口处按代次和载荷摘要拦截，补上 E3c 剩下的窗口。
  3. 租约续约，以及控制面重启和多实例场景。
  4. 与 V1–V5 的 Go 桩合并为同一套表结构（node_exec / results / business_requests / attempts）。
